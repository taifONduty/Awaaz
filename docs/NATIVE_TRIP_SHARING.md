# Native sharing transport

16 October 2026. This increment implements the scoped backend credential and Android transport. The subsequent public-controls increment connects explicit background consent and publisher handoff; its runtime verification is recorded separately below.

## Credential boundary

Migration 10 adds a private immutable device binding for each share. The client generates a 256-bit random credential in Kotlin and stores it with a separate Android Keystore AES-GCM key. Only the SHA-256 digest, domain separated by `awaaz-share-device-v1` and a null byte, crosses Flutter for authenticated binding. The API never returns or stores the raw credential. A Supabase access/refresh token never enters native storage.

The credential grants exactly one share's minimal status, latest-position upload and stop. It cannot read locations, recipients, profiles, Circles or reports. Its deadline is the original fixed share expiry, at most two hours. Identical binding retries do not extend that deadline. A different credential cannot replace the original binding; owner revocation also creates a tombstone when no binding exists, preventing delayed registration from undoing it. A new device requires a new share/consent. Existing membership epochs, blocks, closure, point freshness, sequence ordering and replay rules still govern uploads.

| Endpoint | Authentication | Purpose |
| --- | --- | --- |
| `POST /v1/shares/:shareId/device` | Account | Bind the native credential digest |
| `GET /v1/shares/:shareId/device` | Account | Read minimal binding status |
| `DELETE /v1/shares/:shareId/device` | Account | Irreversibly disable that device |
| `GET /v1/share-devices/:shareId` | Scoped credential | Read status/sequence/deadline; no location |
| `PUT /v1/share-devices/:shareId/position` | Scoped credential | Publish one recent position |
| `DELETE /v1/share-devices/:shareId` | Scoped credential | Stop that share and erase its point/audience |

All responses are no-store. A separate per-credential rate gate supplements the IP gate. Raw headers, request bodies, coordinates, credentials and private IDs are excluded from application logs. Direct table access and helper execution remain denied to API/client roles; readiness checks enforce the restricted grants.

The device revocation endpoint disables future device operations; it is distinct from stopping the whole share. A revoked device cannot stop later foreground owner uploads. While a native device is bound, new JWT foreground position writes receive `native_publisher_active` (409); identical already-accepted point retries remain safe. The native-only internal upload entry is not executable directly by client/API roles. Binding, owner foreground writes and device revocation serialize on the account lock, so a delayed foreground request cannot alternate the live position with the native device. A valid credential can still obtain an idempotent terminal stop receipt after the share ended. Only its digest and minimal binding/revocation metadata remain with the consent tombstone, cascading on account deletion.

## Android ownership and lifecycle

`ShareLocationService` is non-exported and uses the location foreground-service type. Starting it requires a visible activity, precise location permission, enabled notifications and a confirmed active device grant. This follows Android's [while-in-use foreground-service restrictions](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start). It does not request background-location permission or auto-start capture at boot. A native preparation nonce binds activation to a recent visible attempt; server time and request latency produce a conservative monotonic deadline which a retry cannot extend.

The separate native sharing channel exposes only sanitized state and a preparation digest/nonce. The existing app-level native account binding also stops sharing capture when identity changes. Process loss does not silently restart capture: a subsequent read converts interrupted work into stop delivery. Old notification actions carry their exact share ID and cannot stop a different share. The route monitor remains independent; its notification now points to Circle controls instead of falsely asserting that sharing is off.

Capture uses the platform location provider, with fused-provider fallback, rejecting mock fixes, fixes older than eight seconds, accuracy outside 1–50 metres and coordinates outside the Dhaka pilot. Uploads are paced about 15 seconds apart, keep at most one encrypted unacknowledged sample, and replay its exact sequence/payload. A definitive sequence refusal reconciles minimal server state before another sample. HTTP redirects are disabled, bodies are bounded, socket timeouts and a total disconnect deadline bound requests, and a short per-request wake lock supports delivery after the screen turns off. Production origins require HTTPS; debug cleartext is limited to the owned local fixture origin.

Stop halts capture first and saves its intent before delivery. The existing foreground service briefly changes its notification to “Location updates stopped / Confirming the remote stop”, allowing bounded completion work without further GPS samples. It ends after a terminal receipt or a 30-second grace period. One short retry supplements the persisted `JobService`; that job only retries a previously requested stop and never requests location or starts a location service. A lost stop acknowledgement remains pending until an idempotent terminal receipt arrives. Permanent credential refusal records `stop_unconfirmed`, not a claim that the whole share stopped; foreground account reconciliation must resolve it. Pending cleanup can temporarily prevent a new native session. Ordinary job scheduling, force-stop, reboot, Doze and OEM policies still limit when delivery runs.

Android DELETE delivery uses an explicit empty JSON body and content type. The initial platform request was rejected with HTTP 415; this was observed in the sanitized native status log. Opening the app also requeues an encrypted pending stop, because force-stop can cancel its scheduled OS job. Neither path restarts capture.

## Public controls increment

The Circle sharing page keeps foreground consent as its default. Android users can explicitly choose **Keep sharing when locked** for the existing named recipients and original end time. Cancel does not bind a device or start capture. The handoff cancels Dart capture before permission checks/binding and prevents foreground publishing throughout an uncertain result. Native and authenticated API states are reconciled when reopening the page; an interrupted acknowledgement cannot authorize a second publisher. Pause removes native location callbacks; resuming requires another visible audience/end-time confirmation. Leaving the page does not stop an explicitly approved background service.

The page distinguishes background running, paused and unconfirmed states and labels the last server-received timestamp. Native permission requests check the sharing notification channel rather than requiring the route-monitor channel. User Stop first attempts to halt native capture, then obtains the whole-share API receipt; errors remain visible. Removing the last recipient also ends matching native capture. Owner/account epochs invalidate delayed approvals. Both page copy and native sharing/stop-delivery notifications support English/Bangla. A permanent unavailable/revoked device can be ended with whole-share Stop and a new explicit share; it is not silently replaced.

The consumer Android cycle passed in **108 seconds**, process **3884**. It starts with the actual Geolocator foreground publisher, verifies cancel without binding/capture, then uses the rendered background consent, pause and fresh resume confirmation. It verifies the unchanged end time, native handoff with Dart publishing off, a new committed position while the screen is asleep, recipient access, the actual notification Stop action, a discarded committed stop acknowledgement followed by replay, old-consent refusal and account-change capture shutdown. This run uses English consumer controls; Bangla copy/notifications compile, but this record does not claim a Bangla notification runtime check.

The first two consumer runs confirmed cancel, foreground publishing, native activation and pause, then failed the resume assertion with `network_unavailable`. A System UI ANR was also observed between runs and its visible Wait control was used; that observation does not establish the cause of the HTTP failure. The next revision replaces the redundant Dart GPS acquisition during native activation with a purpose-specific precise-location permission request. The native service alone obtains/validates background fixes. Network errors in background mode now say the result is unconfirmed rather than asserting that capture is paused. Fixture-only route-template timing logs supplement the next run without recording credentials, bodies or private IDs.

The next run stopped at the initial foreground GPS acquisition with `location_timeout`: setup had injected only one HAL fix before the slow debug startup. The fixture now supplies bounded, fresh stationary HAL fixes every three seconds, for at most three minutes. It waits for that pulse to stop before the background observer records its marker and injects the distinct test position. The passing run therefore exercises real Android location providers/production upload code, with synthetic HAL input and no SQL-inserted position. No APK or production timeout was changed to repair this fixture timing. No app-data reset or forced scheduler execution was used in the passing consumer cycle.
