# Explicit monitored-route replacement

15 October 2026. The real-graph replacement/alert/acknowledgement/stop cycle is reviewed on the emulator. The final presentation build and the exact limits of that review are recorded below.

## Behavior and boundaries

An active geographic journey can open **Change route**. The destination and travel mode remain fixed. An explicit location-sharing dialog precedes a fresh quality-gated origin fix and the existing routing API. A temporary comparison owns its candidate results; lookup and selection never mutate the current journey, native session or baseline. The view reuses Material route choices, the actual candidate polyline, evidence uncertainty and English/Bangla copy.

Using a candidate requires a second confirmation. The journey retains that approved intent while the native command is in flight. Flutter only commits the new route/origin after an active native receipt matches the previous owner/session, selected route UUID and exactly the next revision. A timeout remains unconfirmed; an explicit status check reconciles it. A late accepted receipt can still update the journey after the comparison page is disposed. It is never automatically resent. A confirmed unchanged baseline permits another explicit attempt. Changed owners/sessions, expiry, stopped monitoring and stale candidate responses cannot authorize a new baseline.

Backgrounding or leaving a comparison discards unapproved candidate results and cancels pending location/HTTP work. Account changes clear candidates and hide the captured destination. An approved command can already have reached Android; leaving its page does not claim to cancel that command. The normal journey owns subsequent reconciliation. Ending the journey requires a native stop receipt even when the local status is unknown/inactive; the Explore fast path now also exposes unavailable-status recovery.

The native bundle now carries `routeValidUntilEpochMs`. Real corridors require a future lease no more than five minutes away. Android checks it while parsing and immediately before starting/replacing the baseline. Debug-only synthetic fixture corridors may omit it; an explicit expired synthetic lease is still rejected. This lease governs acceptance of a route, not continuous monitoring duration, which retains the existing monotonic session deadline. Replacing a baseline resets the deviation detector and requests reliable observation on the newly approved corridor; it does not extend the original session deadline or enable sharing.

The existing API still supplies static-speed estimates, unknown safety and potentially sparse reviewed evidence. Looking up a replacement does not establish that it is safer, traffic-aware or a validated entrance. Physical GPS/OEM behavior, representative startup performance, hosted Auth, public moderation operations and contact delivery remain separate release gates.

Selecting its observed Wait action eventually reaches Explore in the original Awaaz process 2143. No Awaaz activity ANR is recorded at that observation. A temporary local VM-service inspector reads only the existing view-model state; stored/output route and session identifiers are SHA-256 hashes, and private VM connection addresses are not printed. Before/during lookup, the native-receipt snapshot remains active/tracking at revision 1 with identical session and route hashes.

A public mapped waypoint along that path supplies the emulated new origin. The candidate is 4 min / 3.4 km. The journey map and planned estimate update to the accepted 4 min / 3.4 km route. No automatic command resend occurs.

The expired-attempt review finds a UI problem: failure text is above a scrolled candidate and is easy to miss. The subsequent presentation build adds a visible action-result snackbar and replacement-specific expiry wording in both languages. The functional screenshots here belong to the APK above.

## Replacement-baseline alert and stop cycle

After stopping the owned steady GPS fixture stream, the emulator is sent Home and Sleep. An immediate check and then a stricter bounded sleep check do not satisfy the HAL condition. Inspection finds `mWakefulness=Asleep`, `mWakefulnessChanging=false`, display-controller `mScreenState=OFF` and **`mHalInteractiveModeEnabled=true`**. The subsequent trace explicitly accepts only the observed framework-asleep/display-off condition and records the HAL hint as true; it does not present this as full hardware sleep, Doze or physical-device evidence.

Three five-second synthetic on-route samples qualify the newly accepted corridor, followed by eight off-route samples five seconds apart. Android posts check-in notification 7102 with ongoing notification 7101 still present, while the final framework state remains asleep. Returning brings the existing activity forward without a process restart. Its native-receipt snapshot is active/check_in at revision 2 with the same accepted route/session hashes. The actual check-in UI acknowledges the detour, clears notification 7102 and keeps revision 2 and both hashes unchanged. End journey then returns confirmed stopped, and a service dump contains no `TripMonitorService`. All GPS input is emulator data, not physical-location evidence.

The retained scroll offset initially places the check-in prompt above the visible map. The presentation refinement brings a newly latched check-in to the top in the journey and comparison views, puts comparison check-in controls ahead of route details, and changes acknowledgement wording from “original route” to “this route” so it cannot imply reverting an already accepted replacement.
