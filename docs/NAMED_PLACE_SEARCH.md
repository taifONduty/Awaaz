# Named destination search — Dhaka pilot

Implemented locally, 15 October 2026. A checksum-verified local catalogue now supplies public OSM name search to the API and Flutter destination picker. It contains 36,563 records from the confirmed road extract plus a cached POI extract. No Google Places credential or public Nominatim request is used. The existing Android Maps key remains solely in the map SDK configuration.

## Data and API

`scripts/prepare-places.ps1` downloads one bounded, cached operator POI extract for the fixed Dhaka pilot area. It rejects XML errors, external entities and unexpected size before promotion. `backend/routing/export_places.py` runs offline with Python 3.11+, verifies the road extract checksum against the confirmed manifest and emits only allowlisted names, aliases, kind and representative coordinates. OSM author/user IDs, edit histories, contact fields and original raw tags are excluded. Private/no-access and explicitly disused/abandoned features are excluded. Bus-stop tagging is distinguished from ordinary roads.

Mapped nodes keep their positions. Ways/relations use an actual mapped vertex near their bounding-box centre; incomplete geometry is omitted. These positions are approximate browse points, not validated entrances. Import coverage, mapping mistakes, stale businesses and untagged access constraints remain limitations. The current combined source timestamp is `2026-10-13T18:46:47Z`; the catalogue JSON is 9,305,511 bytes with SHA-256 `1be8b57cda0f949bb5ecd29a0f6a8ed9ef4599233787400f4539631caece5190`.

`AWAAZ_PLACE_CATALOG_FILE` supplies the absolute catalogue JSON path. Its companion SHA-256 manifest must match the bytes and configured routing graph version. The loader bounds file size, record/alias/name counts, IDs and pilot coordinates. Source timestamps cannot be implausibly future-dated. Configuration fails rather than silently loading a different graph/catalogue. Imports are refreshed by an operator; the server does not scrape external providers per user.

`POST /v1/places/search` accepts only a bounded query, returns at most eight allowlisted results with graph/dataset/source provenance and explicit `imported_places_only` coverage, and creates no query or trip history. It requests no GPS. Names are Unicode-normalized; exact/prefix/token matches rank deterministically. Nearby identical named/kind records are deduplicated, preserving distinct categories or distant locations. These relevance scores are not safety scores. Missing configuration returns unavailable; no match returns an empty list. Existing request logging excludes bodies/queries and responses are no-store. Shared-IP/load behavior remains a production validation gate.

## Picker behavior

The map picker opens a dedicated search page with one field, ordinary result rows and localized category labels. English/Bangla names use source-language variants where present, with the original name as fallback. The field is debounced; independent cancellation, a six-second deadline, byte/DTO validation and request-generation guards reject outdated results. Navigation/backgrounding cancel searches. Returning from background offers an explicit retry and does not silently resend the query. Personalized keyboard learning, suggestions and autocorrection are disabled for this field; that is an input setting, not a guarantee about every keyboard implementation.

Search words are sent to Awaaz as disclosed in the UI. Imported-data limitations and linked OSM attribution are visible in the results scroller. At large text sizes the notice scrolls with the rows, while the field stays reachable. The picker itself scrolls on short screens/large text rather than compressing the arrival-point confirmation.

Choosing a result moves a review pin and preserves the bilingual destination name. It does not begin routing or monitoring. The user must explicitly confirm the arrival point. A manual pin/coordinate change clears the named association. Planning still obtains a separately consented fresh origin and applies the routing backend's pilot/snap constraints; failed snapping never becomes a fictional route. No favorites, personal recent-history store, live opening hours, verified accessibility or comprehensive address geocoding is implied.

## Reproduce and verification

Run `scripts/prepare-places.ps1`, then Python 3.11+ `backend/routing/export_places.py --root <absolute repository directory>`. Set `AWAAZ_PLACE_CATALOG_FILE` in the API/fixture environment and restart that process. `start-test-postgres.ps1` preserves this ignored local setting. The OpenAPI includes the search contract.

All 24 API cases and 16 focused Flutter UI/geographic cases pass. One added API contract scenario covers bilingual lookup, deduplication, no-store/allowlisting, empty results, rejected private request fields and graph mismatch. One added large-text Flutter scenario checks late-result rejection and explicit point confirmation in English/Bangla at 320 px / 200% text. Review exposed an inaccessible result when the fixed notice took too much room; the notice now scrolls with the results. Static analysis is clean. No database migration or native-monitor logic changed. The full Android restart suite is not presented as a new run for this increment.

Installed emulator review typed `University of Dhaka` using the real keyboard, received genuine catalogue results, selected the education feature and reviewed its actual mapped point. Explicit confirmation preserved the destination name; a separately consented emulated origin produced a real street route of 5 min / 3.9 km, with unknown safety and a static-time disclaimer. Switching language preserved the Bengali destination name. An English query `Farmgate` in the Bangla UI returned localized names/categories; backgrounding and returning displayed the paused state, and explicit Retry restored results. Monitoring remained off. Hardware GPS emulation is not physical-phone location evidence.

This design uses an operated local dataset for typeahead. The [OSMF public Nominatim policy](https://operations.osmfoundation.org/policies/nominatim/) excludes client-side autocomplete on that public service. [OSM XML elements](https://wiki.openstreetmap.org/wiki/OSM_XML) and the [data model](https://wiki.openstreetmap.org/wiki/Elements) describe the node/way/relation basis. Production dataset refresh/quality review, hosting, full geocoding, physical-device performance and the existing Auth/delivery gates remain unfinished. The earlier cold-start stall remains open.
