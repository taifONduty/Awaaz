# First-frame startup and service ownership

## Foreground-only Geolocator configuration, 15 October 2026

Awaaz now overrides the vendored Android library's `geolocator_bind_foreground_service` boolean to false in its application resources. The library default remains true. Engine attachment skips binding the plugin service when disabled; detach only unbinds a successful binding, and a stale connection callback after detach is ignored. The foreground location stream uses its existing client without requiring that service. Requests with `foregroundNotificationConfig` still require a service and now return an explicit acquisition error if it is unavailable.

The production `GeolocatorLocationSource` remains the same Fused Location/permission/timestamp/accuracy path, with its existing cancellation ownership and NMEA opt-out. Awaaz's `TripMonitorService` continues to own native background monitoring. No global dependency cache, alternate GPS provider, notification permission or monitor threshold was changed. [Downstream patch](../third_party/geolocator_android/PATCH.md) records the consumer resource override.

Static analysis is clean (46.2 seconds) and all five existing native engine/parser tests pass after recompilation (3 minutes 55 seconds). The focused Android entry point `integration_test/foreground_location_test.dart` passed in process 3420 in 47 seconds. It uses the production foreground adapter with authorized emulator GPS/permission fixtures: capture, cancellation/reacquisition, the explicit unavailable-plugin-service error, a new capture after that error, and actual Awaaz monitor arming/tracking/confirmed stop. During that cycle, live ADB inspection showed `TripMonitorService` with `isForeground=true` and no Geolocator plugin service. Both services were absent after completion. This does not rerun screen-off deviation/Doze or physical-device scenarios.

The first run stopped on a fixture-only HTTP idle timeout while polling for a native location dialog. That helper now extends only its own socket lifetime, cancels pending ADB work when its client leaves, and requires a successful fresh UI dump at a unique path before a native dialog click. TypeScript checks pass. The retry used the same APK; no production timeout or location threshold was relaxed.

The integration APK builds in 257.9 seconds: 105,939,409 bytes, SHA-256 `0ecde54b79ac6f1742f9e2409221801a1e4e508646021923fef70017e454f778`. The regular Maps preview builds in 254.9 seconds: 108,493,785 bytes, SHA-256 `099961e5f1423a2d1e7f26c03f214faadb5ddcec4bbf030adf98c86ff1621ff3`. AAPT inspection confirms the merged resource is false in both APKs; the integration APK's binary manifest excludes the Maps key. The fixture run began only after the launcher's System UI ANR had cleared; Awaaz was not running when that dialog appeared. The regular preview's cold-launch and Map controls are reviewed separately below. No claim that every startup ANR is resolved follows from this service change.

## Later service timeout, 15 October 2026

During restoration after sharing-backend verification, the unchanged contact-block preview (`81c8b4ab22d82935e1324bae70ca0b7a58a58e5244b4f9e557960c7df3954011`) reproduced ANRs. ActivityManager identified Awaaz process 2458 waiting 20,255 ms while executing `com.baseflow.geolocator.GeolocatorLocationService`. System UI and Settings also became unresponsive in the same boot; the Settings reason was an unresponsive content provider. Activity `lastanr` still reported no activity ANR, so that dump alone would have missed the service failure.

The observed Wait actions returned the same process to real Maps. Initial native lookup was explicitly unconfirmed; after retry, read-only VM inspection confirmed inactive/stopped, revision 0, with no route or session. `TripMonitorService` was absent. Further ANR dialogs appeared, so the owned API/router was stopped and Awaaz explicitly force-stopped for a launch without concurrent graph loading. This recovery does not resolve the defect or establish a production startup time.

Source inspection identifies a concrete dependency to isolate next: the vendored Geolocator plugin binds its background service unconditionally in `onAttachedToEngine`. Its stream handler also requires that service even for the separate foreground-only location-client path. Awaaz already uses its own native trip-monitor service, and no Flutter location request supplies `foregroundNotificationConfig`. Deferring or opting out of the unused plugin service needs a scoped implementation and verification of foreground GPS/cancellation; changing it has not yet been tested. The service timeout identifies the failing lifecycle component, not proof that this eager bind is the sole cause. Host scheduling, plugin/Flutter initialization and representative-device behavior remain open.

With the local API/router stopped, an explicit force-stop/relaunch reached real Maps in new process 3701 without a dialog in the reviewed screenshot. Read-only inspection confirms inactive/stopped, revision 0, no route/session and confirmed native status. [Recovered preview](ui-redesign/sharing-backend-recovered-preview.png). The fixture API was restarted only after that app state settled. This ordering helped this run; no startup fix or representative-device timing is established.

14 October 2026. `main.dart` now calls `runApp` immediately after binding initialization. `AwaazStartup` renders a small branded loading surface and starts account/session setup after that framework frame. It then mounts the normal application with the initialized services. Auth/storage initialization no longer precedes the first Flutter frame.

The startup container owns the account view model it creates. It disposes it when removed, including when an in-flight initialization completes after removal. Injected view models used by other application callers remain caller-owned. Initialization errors expose the existing configuration-problem state without logging credentials or exception details. No account data is shown while initialization is pending, and no network request is retried automatically.

Two coordinate-free timeline markers identify the first framework frame (`awaaz.startup.first_frame`) and account initialization interval (`awaaz.startup.accounts`). The first marker records a framework callback, not proof of the first frame reaching the display. These traces are diagnostic aids, not performance scores.

## Evidence and limits

The existing UI suite has one added lifecycle scenario verifying that delayed account initialization leaves the loading surface rendered, late services are disposed after unmount, successful initialization mounts the normal app, and its owned services are released on removal. All 12 UI cases pass; static analysis is clean. This check concerns a consequential startup/lifecycle boundary, rather than cosmetic rendering.

The preceding APK encountered a System UI ANR and an Awaaz focus-dispatch ANR during emulator cold boot. Android reported 98% total CPU with substantial kernel/swapping activity. The sampled Flutter/native main-thread wait does not establish a particular application deadlock or prove that first-frame sequencing caused it. The startup change addresses an independently observed code issue; the ANR must remain open until stronger evidence identifies and verifies its cause.

The updated debug APK builds in 172.4 seconds; installed-build results are recorded below. The local backend is kept stopped during emulator boot to reduce competing load; it starts only after the application review. That workflow adjustment does not establish production performance. Flutter recommends performance profiling on a physical device in profile mode; debug/emulator timing is not release-performance evidence. [Official profiling guidance](https://docs.flutter.dev/perf/ui-performance).

The APK is 108,416,440 bytes with SHA-256 `F8C7A34808E114D9C288E031656B07C0F5A695E42D7F796E2D3294DA5F2A12AC`. A cold launch reached Explore in process 2235 without a recorded Android ANR in this boot. `am start -W` reported timeout after 15,225 ms while the native shield splash remained visible; the same live process subsequently exposed the normal home UI. One warm relaunch similarly timed out after 16,068 ms, then reached Explore in process 3052 without a recorded ANR. Navigation and English/Bangla switching worked afterward. These observations do not establish exact frame timings, eliminate slow startup, or prove the previous ANR's cause was fixed. System memory pressure remains a confounder; live inspection showed about 446 MiB free RAM and 1,996 MiB in the host's C: pagefile.

The app is returned to English Explore with monitoring off, and the local fixture backend is restarted after the navigation review. [Installed screen](ui-redesign/startup-final-explore-android.png). Previous monitor/route verification belongs to its earlier APK; the native monitor and API were not changed or retested in this startup-only increment. The existing full Android restart suite remains separate evidence.

Hosted Auth initialization, representative physical-phone cold starts, low-end device memory pressure, OEM background limits and release/profile-mode frame analysis remain verification gates. No connected physical phone is currently available.

## 15 October: status recovery and ANR diagnosis

The named-search APK reproduced both System UI and Awaaz ANR dialogs during a later cold boot. The preceding successful launch does not establish that startup is fixed. Decoding the latest recorded native offsets against the locally cached x86-64 debug engine, with matching ELF build ID `07237bcbd2ff3d70a31cea404af9e4403c13fba4`, identifies `dart::OS::GetCurrentThreadCPUMicros`, `dart::CompileFunctionHelper`, `dart::Compiler::CompileFunction`, `dart::Function::EnsureHasCodeNoThrow` and JIT inline-cache miss handling. This sample shows debug compilation on the sampled thread; it does not establish a deadlock, isolate the offending Dart function, or exclude host pressure and other causes.

Native status synchronization now has an explicit unconfirmed state, separate from a failed user command. An unsuccessful initial owner binding shows “Monitoring status unavailable” with Retry, rather than claiming monitoring is off or explaining an unrelated preview corridor. Retry repeats the owner binding when needed. A failed status read retains the last trip snapshot but marks it unconfirmed; arming requires a successful reconciliation first. A successful native event/read clears the synchronization warning. English/Bangla copy and a large-text Retry action are included. No retry automatically arms a service or changes the route baseline.

The focused monitor suite passes all 12 cases, including one new binding/reconciliation boundary case and recovery through the existing Bangla large-text panel flow. Static analysis reports no issues. This does not verify the unresolved ANR or physical-phone behavior.

`scripts/build-android.ps1 -Mode profile -UseMirrors -StopBuildDaemon` provides a separate local AOT profile APK for a controlled startup comparison. The default remains the debug preview; integration fixtures require debug mode. Flutter's profile build inherits the local debug signing configuration and remains unsuitable for distribution. Emulator profile results are diagnostic observations, not production performance measurements.

The shell now requires a confirmed inactive native snapshot before ending a visible journey. A failed or pending binding must not silently discard that journey. The final focused run passes all 12 monitor cases; changed-source analysis reports no issues. The earlier full-package analysis was also clean before the final shell guard.
